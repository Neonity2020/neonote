# ADR-0007：双链以纯文本形式存在于正文

- **状态**：已接受
- **日期**：2026-10-20

---

## 背景

要实现 Notion / Obsidian 式的**双链**：正文里写 `[[页面标题]]` 就能链接到另一个页面，
被链接的页面能看到"谁引用了我"。

关键约束来自这个代码库已有的形态：

1. 块正文是**纯文本**，存进 `blocks.content` 的 JSON 里，渲染层用 `contentEditable` 直接编辑。
2. **没有 schema 迁移机制**（见 [ADR-0001](0001-local-first-sqlite.md)），
   加表意味着要处理已有数据库的升级路径。
3. 块编辑是**高频**操作，400ms 防抖落库，页面切换前还要 `flushSaves()`。

需要决定三件事：

- 链接**存**在哪：正文里，还是单独的表？
- 链接**指向**什么：标题，还是页面 id？
- 链接**怎么渲染**：在 `contentEditable` 里怎么显示成可点击的链接？

---

## 决策

### 1. 链接就是正文里的纯文本

`[[页面标题]]` 是块正文的一段普通字符，**没有独立的表、没有独立的字段**。
出链和反链都是**查询时解析**出来的。

```
blocks.content.text = "详见 [[计划]] 这一页的排版"
         ↓ 查询时解析
出链:  计划 → pageId
反链:  谁写了 [[本页标题]]
```

### 2. 以标题为标识，支持改名传播

链接的目标由**标题**决定（与 Obsidian 一致）。
解析时先精确匹配，再退回忽略大小写匹配。

页面改名时，主进程**自动改写全库**指向旧标题的链接。
**但只有旧标题在库里唯一时才改写**——存在同名页面时保持原样，把判断权留给用户。

### 3. 装饰器绝不修改文本

渲染层把 `[[标题]]` **原样**包进 `span.wiki-link`：

- **方括号保持可见**，不做视觉隐藏。
- `element.textContent` 与数据库内容**逐字一致**。
- 装饰器带签名（`data-wiki-sig`），结构没变就不重建 DOM。
- 重建时用文本偏移把光标放回原位。

### 4. 查询词延伸到光标

输入 `[[` 唤起选择器时，`[[` 到**光标**之间的全部内容是查询词，
选中后整段被替换（与 Obsidian 一致）。

---

## 理由

### 为什么不用单独的表

考虑过 `page_links(source_id, target_id, block_id)` 这样的关系表。

不用的原因：

| 问题 | 说明 |
| --- | --- |
| **要维护** | 每次块内容改动都得同步这张表。写操作散落在十几处，漏一处就出现"正文和索引对不上" |
| **改标题要迁移** | 标题是标识，改名时既要改正文又要改索引，两处必须原子完成 |
| **没有迁移机制** | 新表需要版本表 + 迁移函数，否则老数据库打不开（[ADR-0001](0001-local-first-sqlite.md)） |
| **本地数据量小** | 一次反链查询是"扫一遍含 `[[` 的块"，用 `instr(content, '[[') > 0` 就能过滤掉绝大多数块 |

**正文即索引**的最大好处是**永远不会不一致**——链接的真身只有一份。
代价是查询要现算，对本地 SQLite 来说完全够用。

### 为什么用标题而不是页面 id

如果链接存 id，正文会变成 `[[3f2a...]]` 这样的机器串——不可读、不可手写、
改名后还得维护一张 id→标题的映射（而正文里还留着旧标题，两边又对不上了）。

用标题的代价是**改名会让链接失效**。这个代价用"改名自动传播"来消解，
并且传播有唯一性保护，不会把链接指错。

### 为什么方括号保持可见

试过把方括号用 CSS 隐藏（`display:none` / `font-size:0`），视觉上更干净。但：

- `display:none` 的内容在部分浏览器的**复制**行为里会被丢掉，
  复制出去的链接就没有 `[[]]` 了。
- 隐藏的字符**不能放置光标**，用户无法把光标移进链接里编辑。
- 偏移计算要额外维护"装饰态 ↔ 原文"的映射，容易出错。

保持可见让 `element.textContent` 天然等于原文，
`getCaretOffset` / `setCaretOffset` 也就**天然对齐**——
这是整个渲染层最省心、也最不容易出 bug 的选择。

方括号可见也是许多 wiki 工具的默认形态（Obsidian 源码模式、Logseq、Foam）。

### 为什么签名机制

装饰器每次都重建 DOM 会打断光标。但**每次输入都重建**又会让编辑变得粘滞。

签名由「链接区间 + 目标是否存在」组成：

```
start-end:title:exists|start-end:title:exists
```

- 纯文字改动**不会**改变签名 → 跳过重建。
- 浏览器偶尔会合并/拆分文本节点，签名不变不代表 DOM 还完好，
  所以重建前还会比对一遍 span 的数量和文本。

---

## 后果

### 正面

- **没有第二份真相**。链接只存在于正文里，不可能和索引对不上。
- **不需要 schema 迁移**。新功能完全在现有结构内实现。
- **搜索与 AI 自动兼容**。链接就是文本，`LIKE` 和 `json_extract` 照常工作。
- **正文可读可复制**。链接带 `[[]]` 语法，复制到别的工具仍能识别。
- **改名不会断链**，且有唯一性保护，不会指错。

### 负面

- **反链查询要全表扫**。数据量大时会变慢，届时可加 FTS5 或物化一张表。
- **同名页面有歧义**。解析按"精确优先、再忽略大小写"，取列表里第一个。
  系统不阻止重名，但改名传播在有歧义时会保守地不改写。
- **改名传播是 O(全库)**。改名时扫一遍含 `[[` 的块并改写。对本地库够用。
- **方括号可见**，视觉上比"隐藏括号"的 wiki 工具稍吵。

### 后续影响

- 链接的解析函数必须**主进程与渲染进程共用同一份**（`packages/shared`），
  否则"界面上显示能点开"和"面板里统计成反链"会指向不同的页面。
- 装饰器**绝不能修改文本**。任何"顺手把 `[[标题]]` 换成纯文本"的想法都要拒绝。
- 新增块类型时，如果它也能写链接，要记得它是否需要装饰。
