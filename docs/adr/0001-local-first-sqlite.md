# ADR-0001：本地优先，SQLite 单文件存储

- **状态**：已接受
- **日期**：2026-10-14

---

## 背景

做一个块编辑器应用（Notion 的本地化版本）。核心需求是：

- 页面和块要持久化，且**不能丢**。
- 要能全文搜索。
- 要能存图片。
- 桌面端（Electron），主要在 Windows 和 macOS 上。
- 产品定位是"本地优先"——数据在用户机器上，不依赖服务器。

关键约束：**没有后端**。所有数据操作都在本地完成。

---

## 决策

用 **Node 内置的 `node:sqlite`（`DatabaseSync`）**，在 Electron 主进程里管理**一个数据库文件**：

```
<userData>/notion-clone.db
```

- 三张表：`pages`、`blocks`、`settings`。
- 外键级联删除（`ON DELETE CASCADE` + `PRAGMA foreign_keys = ON`）。
- WAL 日志模式。
- 图片**不进数据库**，存文件系统，数据库只存引用。

---

## 理由

### 为什么不建服务器

这是产品定位的决定，不是技术选择。"本地优先"意味着：

- 离线完全可用。
- 没有账号系统、没有 API 密钥管理。
- 没有服务器成本和运维成本。
- 用户的数据**天然**在自己手里。

代价是没有多设备同步。接受这个代价。

### 为什么用 SQLite 而不是 IndexedDB

IndexedDB 是 Web 平台的标准存储，浏览器里有，但 **Electron 主进程里没有**，
渲染进程里有但主进程访问不便（要跨进程调用）。

选 SQLite 的具体原因：

| 原因 | 说明 |
| --- | --- |
| **同步 API** | `DatabaseSync` 是同步的，代码里不需要 await，逻辑线性可读 |
| **主进程原生** | 渲染进程没有 Node 能力，SQLite 天然住在主进程 |
| **一个文件** | 备份 = 复制一个文件。简单到可以写进用户文档 |
| **SQL 能力** | 搜索能用 `json_extract` 在数据库里直接过滤，不用全量读进内存 |
| **无原生依赖** | `node:sqlite` 是 Node 内置模块，不用编译 `better-sqlite3` 之类的原生包，跨平台打包无坑 |

### 为什么不选 better-sqlite3

需要原生编译。electron-builder 要为每个平台单独重建，CI 复杂度和失败率高很多。
`node:sqlite` 零依赖。

### 为什么图片不进数据库

图片是**大块二进制**。放进 BLOB 会让：

- 数据库文件迅速膨胀，WAL 日志也跟着变大。
- 每次备份都要复制所有图片。
- 渲染层要处理 data URL 或 BLOB 的 base64 开销。

拆开之后：

- 数据库只存几十字节的引用。
- 图片可以被 HTTP 缓存、可以被单独替换。
- 备份时可以分别处理（虽然最终还是一起复制）。

代价是两者可能不一致（手动删文件 → 破图），需要 GC 机制兜底。

---

## 后果

### 正面

- 单文件存储，备份和迁移成本极低。
- 无服务器成本，无网络依赖。
- 同步 API 让数据层代码线性、易读。
- 打包无原生依赖问题。

### 负面

- **没有多设备同步。** 换机器要手动拷贝数据目录。
- **没有多人协作。** 这是单人应用。
- **没有版本历史。** 删错内容无法恢复。
- **没有迁移机制。** `CREATE TABLE IF NOT EXISTS` 不会改动已存在的表。
  加字段要么手写 `ALTER TABLE`（用户手动操作，不现实），
  要么引入版本表 + 迁移框架，要么删库重建（丢数据）。

### 后续影响

- **新增字段优先扩展 `content` 的 JSON 形状**，而不是加列——
  JSON 字段不需要改表结构，旧数据读出来该字段为 `undefined` 即可。
  见 [ADR-0003](0003-json-block-content.md)。
- 如果将来要支持 schema 升级，需要补一个 `schema_version` 表和版本化迁移函数。
- 未来若要做同步，SQLite + 单文件是个**好起点**——
  同步本质上是把这个文件（或它的变更日志）与远端对齐。
