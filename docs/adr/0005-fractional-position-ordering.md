# ADR-0005：分数位置排序（position）

- **状态**：已接受
- **日期**：2026-10-14

---

## 背景

页面树和块列表都需要**有序**。排序字段要能：

- 支持在任意位置插入。
- 支持拖拽重排。
- 支持跨层移动页面。

数据量不大（一个笔记应用，几十到几千个块），
但**编辑频率高**——每次打字都可能触发一次位置相关操作。

---

## 决策

用 `position REAL`（浮点数）存排序位置，**步长 `POSITION_STEP = 1024`**。

### 插入到末尾

```ts
const maxPos = SELECT MAX(position) FROM blocks WHERE page_id = ?
position = (maxPos ?? 0) + 1024
```

### 插入到中间

取**前后邻居的中点**：

```ts
if (prev && next) position = (prev.position + next.position) / 2
else if (prev)     position = prev.position + 1024
else if (next)     position = next.position - 1024
else               position = 1024
```

### 整体重排

拖拽结束时整层重写为 `(index + 1) * 1024`，在**单个事务**内完成。

---

## 理由

### 候选一：整数序号

```
position = 1, 2, 3, 4, 5
```

在中间插入需要**重写后面所有行**：

```
插入到位置 2：1, 2, [新], 3, 4, 5 → 所有后续行的 position + 1
```

问题是**写放大**：在第 1 位插入要更新 999 行，在最后一位插入只更新 1 行。
而且块编辑是高频操作，即使只有 1% 的编辑涉及插入，
写放大也会随数据量线性增长。

### 候选二：UUID / 时间戳做键

- 时间戳：同一毫秒内创建的两个块会**撞键**，顺序不确定。
- UUID：完全无序，无法表达"相邻"关系。

UUID v4 是随机的，**没有可比较的顺序**。UUID v7 有时间有序性，
但只能表达"创建先后"，无法表达"我把它拖到了这里"。

### 候选三：分数位置（选中）

浮点数的**中点插入**让"插到两个元素之间"变成一次单行写入：

```
原来：  1024,  2048,  3072
插入后：1024,  1536,  2048,  3072
                ↑ 只需写这一个
```

步长 1024 意味着**相邻两次插入之间有 512 的间隔**，
每次中点插入把间隔减半。512 → 256 → 128 → …
大约 **10 次连续在同一个位置插入**后，间隔会耗尽到 1 以下，
再往下浮点精度就不够了。

**实际影响很小**：块编辑最常见的是"在末尾追加"（走 `max + 1024`，
间隔始终是 1024），而不是"在同一个位置反复插入"。

### 为什么是 1024 而不是别的数

- 足够大 → 中点插入能撑很多次。
- 足够小 → 浮点不会太早耗尽精度（IEEE 754 double 有 53 位尾数，
  1024 尺度下的位置值能精确表示到小数点后约 10 位）。
- **2 的幂** → 除以 2 得到中点时不会引入额外的二进制舍入误差。

### 为什么重排要归一化

拖拽结束后整层重写成 `(index + 1) * 1024`，
把之前中点插入积累的"不规则间隔"**恢复成均匀分布**。

这是**自愈机制**：间隔被压到极限时，一次拖拽就能修复。

### 为什么用 REAL 而不是 INTEGER

中点可能是小数（`(1024 + 2048) / 2 = 1536`，这个是整数，
但 `(1024 + 1536) / 2 = 1280` 也是整数——
实际上 1024 是 2 的幂，前几次中点仍是整数）。

但**理论上**中点可以是任意实数，而且 `position` 的语义是"顺序"而不是"数量"，
用 REAL 更诚实，也避免将来调整步长时被整数假设绑住。

SQLite 的 `REAL` 是 8 字节 double，存储开销可以忽略。

### 为什么页面和块用同一套策略

两者都是"有序列表 + 支持中间插入 + 支持拖拽重排"。
用同一套策略意味着只有一份心智模型、一份实现。

---

## 后果

### 正面

- 中间插入是**单行写入**，没有写放大。
- 排序查询是 `ORDER BY position`，能走 `idx_blocks_page` / `idx_pages_parent` 索引。
- 重排会自愈间隔不均的问题。

### 负面

- **浮点精度有限**。在同一个位置连续插入约 10 次后，间隔会耗尽。
  表现是"插入位置不精确"。
- **位置值不连续**，不能用来表示"第 N 个"——
  想知道序号必须另外算（前端算有序列表编号就是这么做的）。
- **必须成组处理**。重排时要在一个事务里更新整层。
- 位置值会随编辑变得"越来越碎"，只有重排才能整理。

### 后续影响

- **插入逻辑不能简化成"取 max + 1"**。虽然结果也对，
  但那样会让间隔迅速缩到 1，精度问题提前爆发。
  必须用 `POSITION_STEP = 1024`。
- **重排是唯一能修复间隔的手段**。如果用户长期不拖拽，
  间隔会一直保持不均——但这不影响正确性，只影响中点插入的余量。
- 前端计算有序列表编号时**不能依赖 position**，
  而是按渲染顺序遍历计数（见 `Editor.tsx` 的 `numbers`）。
