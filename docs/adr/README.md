# 架构决策记录（ADR）

记录**为什么**这样设计，避免后来者推翻已有的、当时看起来很随意的决定。

---

## 什么时候写

写 ADR 的判断标准：

- ✅ "为什么用 SQLite 而不是 IndexedDB？" —— 会有人问，写。
- ✅ "为什么禁用 Pi 的内置工具？" —— 安全边界，必须写。
- ✅ "为什么 position 是浮点数？" —— 有明确取舍，写。
- ❌ "为什么按钮用 `rounded-md`？" —— 没人会问，不写。

**一句话**：如果一个决定**不显然**，或者未来有人可能会问"为什么这么做"，就写一份。

---

## 规则

1. **已接受的 ADR 不可原地修改。** 想改变决策就写一份新的，在新 ADR 里说明它取代了哪一份。
2. **一份 ADR 记一个决策。**
3. **必须写清楚备选方案**。只写"我们选了 A"没有信息量，要写"为什么不是 B/C"。
4. **必须写清楚后果**，包括不好的那一面。

---

## 状态

| 状态 | 含义 |
| --- | --- |
| 提议中 | 还在讨论，尚未实施 |
| 已接受 | 已实施，是当前系统的既有事实 |
| 已取代 | 被后续 ADR 取代，在文档顶部注明被谁取代 |

---

## 命名

```
NNNN-简短英文-slug.md
```

四位数字顺序编号，slug 用英文小写连字符。

---

## 模板

```markdown
# ADR-NNNN：决策标题

- **状态**：提议中 | 已接受 | 已取代
- **日期**：YYYY-MM-DD
- **取代**：ADR-XXXX（如果有）

## 背景

我们要解决什么问题？当时的约束是什么？

## 决策

我们决定怎么做。

## 理由

为什么选这个方案？有哪些备选方案，为什么不选？

## 后果

### 正面

- ...

### 负面

- ...

### 后续影响

- ...
```
